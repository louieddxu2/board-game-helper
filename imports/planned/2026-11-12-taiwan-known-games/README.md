## 雲端匯入與驗證

1. 寫入前用首批 BGG ID、相關版次、名稱與別名再跑一次正式 D1 唯讀比對。若有新的對應，先確認應沿用哪筆遊戲。
2. 以正式 D1 binding 的單次 `batch()` 執行 [first-batch.sql](first-batch.sql) 的兩個語句。第一個寫入 `games` 的公開主遊戲，第二個寫入 `game_external_ids` 的主 BGG 對應。重複的 BGG ID、版次、名稱或別名會跳過，現有遊戲資料保留。新增遊戲依現有審查規則以 `pending` 建立。
3. 執行 [verify.sql](verify.sql)。回傳 0 列表示首批遊戲、外部 ID、投票主體及全部啟用屬性的初始狀態都已建立。有回傳列時，按該列查明缺失或衝突。
4. 由現有的 `flushCatalogOutbox()` 發布遊戲及屬性目錄增量。使用匯入前的目錄游標從公開 API 驗證 24 款都出現在兩份增量中。屬性增量請帶上快照的 `generation` 與 `generatedAt`。記錄正式執行的 D1 讀寫量。

現有資料庫觸發器會依 BGG ID 建立屬性投票主體及每項屬性的初始狀態。這些狀態的 `evidenceCount` 從 0 開始，取得投票後才有相似遊戲搜尋可使用的評分證據。

知名度順位保留在候選資料，供後續依「大約玩過幾款」調整出題。遊戲身分與投票仍走現有 D1 表及目錄同步流程。這批 SQL 放在 `imports/planned/`，一般部署不會執行。

## 本機試跑

以完整 migration 建立隔離資料庫，確認首批新增 24 筆遊戲、24 筆 BGG 對應及 600 筆屬性初始狀態。再次執行新增語句時寫入 0 筆，既有目錄發布器分別產生 24 筆遊戲與 24 筆屬性主體增量。另以隱藏遊戲、同名別名、既有外部 ID 和已入庫的其他版次各模擬一種衝突，均驗證為跳過新增。
