# 取勝方式：現行規格與驗收

## 唯一計分來源

分數由逐筆評分與比較記錄重播產生。`attribute_score_states` 與 `attribute_pair_stats` 是可重建的衍生資料，不是原始資料；不使用合併前最終分數的平均、彙總種子或「已吸收」票數。

- `attribute_vote_responses` 保存完整回答：兩款遊戲的直接評分、比較、時間與出題方向。
- `attribute_vote_events` 保留較早的逐筆事件。若相同 response ID 已有完整回答，重播時不重複套用事件。
- 按時間及穩定的記錄 ID 排序；每筆依序套用 A 評分、B 評分、比較。
- 沿用 `glicko-rd-v1`；沒有投票時為 5 分、RD 3，首次直接評分使用提交值。

## 雙端與 UI

固定儲存方向：0＝得分取勝，10＝條件取勝。只在抽到雙端屬性時隨機選擇出題高端，直接評分與比較都依該方向轉換回固定方向儲存。瀏覽表固定兩端，排序可切換；原有作者說明不改寫。

最近投票動態維持原設計：僅顯示比較，並附上同次直接評分；不增加純直接評分動態或完整歷史頁。

## 一次性轉移

0090 將舊得分端逐筆轉為 `10 - 評分` 並反轉比較，條件端保留方向；歷史顯示改為新屬性名稱與兩端。原始 ID、時間與投票人資訊保留。0089 曾加入的彙總種子已由 0090 移除。

0091 將作者指定修正落在原始匯入評分，並移除誤加的五筆補票：The Mind 9、第七大陸指定配置 10、And Then We Held Hands 8、Fog of Love 10、花火 2。未修改其他人的線上投票。

0092 清理未使用的初始值／映射程式與四張相容表，資料表非空即中止。已發布遷移檔保留，確保空資料庫可按順序建立。舊的匯入存檔不作為線上重播來源。

## 驗收與操作

正式站在 0091 後已由 131 筆有效重播記錄重建 108 款有資料的遊戲，獨立重算的分數、RD、各項計數差異為 0。這是當時驗收數字，不是往後固定筆數。

唯讀驗證（不改正式資料）：

```powershell
node --import tsx scripts/replay-win-history.ts --verify
```

`--apply` 僅供繼續已排定的 `win-history-replay-v1` 工作，完成後再次執行不會清空重算。一般遊戲合併使用背景重建流程；有作用中的重建工作時暫停寫入投票，避免漏算。

清理版須通過完整測試、型別檢查、建置及 0092 遷移驗證；發布後再執行上述唯讀驗證。0092 尚未因文件更新而自動套用正式站。

設計演進另存於 [歷史紀錄](archive/attribute-win-activation-history.md)，不作為現行操作依據。
