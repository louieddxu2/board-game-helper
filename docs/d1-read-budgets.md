# D1 讀取預算與快取邊界

本文件描述日常操作的架構上限。Cloudflare 的 `rows_read` 可能把索引巡覽列算入，因此數字不是「回傳 JSON 筆數」，但查詢必須維持在指定索引或固定聚合列，不可退回全表掃描。

| 操作 | 本機優先行為 | 快取失效後的 D1 範圍 |
|---|---|---|
| 首頁 | 先顯示 IndexedDB 舊內容，背景更新 | 固定首頁 ID 聚合與少量被引用實體 |
| 遊戲列表 | 先顯示本機總表；10 分鐘後查版本差額；每週重抓總表 | 差額為版本索引命中的變更列；每週總表為預先聚合分塊，不掃 games/rules |
| 登入者目錄 | 與遊戲列表共用同一份本機總表 | 一般使用者只顯示公開數；editor 顯示預先聚合的總數，不另查 games |
| 公共 Tag | 先顯示本機公共 Tag 目錄；每週同步 | 版本索引命中的 Tag 變更列，不 JOIN alias/rule_tags |
| 屬性總表 | 先顯示 IndexedDB 的完整快照；同步檢查每 10 分鐘執行，快照本身每週更新 | 只讀 `attribute_catalog_snapshot_state` 與目前 generation 的分塊；同步時只讀 `(catalog_version, entry_key)` 索引命中的增量列，每批最多 80 列，不掃描 score states、subjects 或 candidates |
| 單款遊戲 | 一小時內直接使用 IndexedDB；過期內容先顯示再背景更新 | 只查該遊戲及該遊戲規則，不查其他遊戲 |
| 規則重要票 | 公開總票數隨規則列取得；本人投票清單快取 10 分鐘 | 個人狀態只走 `(user_id, game_id)` 索引並讀回自己在該遊戲投過的列；投票寫入後只讀 1 列規則確認總數 |
| 一般帳號頁 | 不讀規則活動 | 只回傳 session 中的使用者；editor/admin 才執行最多各 100 筆活動查詢 |
| 收藏首頁 | 本機畫面優先；私人狀態不共用公共快取 | 受固定 LIMIT 與指定遊戲 ID 限制 |
| GeekGroup 收藏 CSV | 只在 IndexedDB 保存去重後的 BGG ID 索引；CSV 的收藏狀態、遊玩次數、私人評分等欄位不進公共資料庫 | 目前不寫 `games` 或 `game_external_ids`；若未來要跨裝置保存，應另建使用者收藏表，不得把收藏資料混入共用遊戲實體 |
| 管理 Tag | 僅管理員主動開啟 | 可讀 active tags、rule_tags 使用量與 aliases；不屬於公共高頻路徑 |
| 屬性比較題目與我的收藏 | 屬性總表載入後，在本機以 IndexedDB 目錄、BGG ID 和抽選狀態選題、換題；不逐題呼叫 Worker | 題目切換本身不查 D1；只有目錄不存在或需要同步／修復時，才走上方屬性總表快照與差額路徑 |
| 屬性近期投票 | IndexedDB 快取 5 分鐘；先顯示舊資料、過期才更新，成功投票使用回應更新本機 | 快取命中不查 D1；失效時沿用時間索引查詢最近 5 筆有效屬性回答，不寫 D1。實際讀取列數取決於資料分布，不以回傳筆數當成讀取上限 |
| 屬性投票送出 | response_id 去重後先保存原始回答或完整排序；收票成功即由雲端負責補算 | 每票只保存 1 筆原始資料。共用計分租約的擁有者每批最多讀 10 筆新票、每次最多 2 批；其他上傳者不讀分數或計分批次。按指定遊戲索引驗證，同批狀態合併後與共用進度原子寫入；不逐票更新完成標記，也不寫 pair_stats 或另一筆 feed。計分失敗不撤銷已收票；既有每日排程可補算。實測、重算交接與成本範圍見 [收票與批次計分](attribute-vote-ingestion.md) |
| 屬性總表背景建立 | 每週判斷是否需要完整重播；大型重播可由每日排程接續，最後原子發布新 generation | 正常即時比較且投票池未變時，沿用快照和增量，不讀投票歷史或 score states。完整重播的歷史 rowid 上界達 4,000 時，以每頁最多 4,000 筆保存輸入，再按屬性暫存結果。每日無進行中的工作時只查一筆工作狀態。手動完整重播仍可直接執行 |
| 遊戲資料健檢 | 只在人工執行 `npm run audit:game-data -- --remote`；結果存於 `.wrangler/game-data-health/`，不進 Git | 只讀 `games`、`game_aliases` 全表各一次（約等於兩表列數），零寫入；比對鍵、BGG ID 重複、名稱重複候選與缺 BGG ID 清單都在本機計算。比對鍵不一致或 BGG ID 重複時結束碼為 1 |
| 網站地圖 `/sitemap.xml` | 只供搜尋引擎讀取；回應標示一天快取，並套用公開讀取的頻率限制 | 只讀遊戲總表快照的狀態列與目前 generation 的分塊（與 `/api/game-catalog` 相同），只列出有公開規則的遊戲 |
| 完整資料匯出 | 無自動呼叫 | 會讀取全部公開資料，所以只允許管理員人工執行，禁止列為公共快取端點 |

寫入上限：訪客與一般會員共用每日 80,000 列的 D1 寫入額度（UTC 每日重置，對齊 D1 免費額度）；其餘 20,000 列留給編輯者、管理員與排程，足以在遭到攻擊的當天仍完成一次完整屬性重算（目前約 5,000–10,000 列，會隨資料成長）。編輯者、管理員、登出與刪除帳號不受限，閱讀不受限。用完後非編輯者的寫入回應 429 `daily_write_budget_exhausted`，畫面說明恢復時間；同一個 Worker 執行環境記住當日已滿，之後拒絕時不再查詢 D1。額度達 80% 起，管理員開啟網頁就會看到提醒。

守門規則：

- 前端不得出現 `fresh`／`force` 參數；需要最新資料時先標記對應本機快取失效，再走同一個 cache-first 函式。
- 遊戲搜尋、目錄與公共 Tag 不可繞過版本化總表直接查資料表。
- 完整匯出不可加入公開讀取或跨站公共快取清單。
- 每日保留單一排程，同時清理匿名瀏覽去重資料、舊統計與過期 session；每週總表也由同一排程的星期判斷執行。
- 屬性重播的歷史頁與游標一起提交。重播中遇到新增直接評分時，停止擴大本輪歷史範圍。截止後已在線上計分的票，發布前依原寫入順序分頁補到重算結果上。直接評分及同批匯入票留到下一輪完整重播，本輪保留待處理修訂。改寫或刪除舊票、權重變動會重開工作。發布前核對最新投票、修訂版本與目錄狀態。暫存表只由背景重播使用，投票送出不寫入暫存表。
- 有待處理修訂的單次完整重播與管理員手動重建，會以即時計分表比對重算結果。這能移除上次檢查點之後曾計入即時計分、後來又被刪除的票。這項讀取發生在完整重播，日常快取更新仍沿用快照和增量。

### 遷移成本驗證

`npm run deploy` 與 `npm run db:migrate:remote` 都必須通過 `scripts/check-migration-row-budget.mjs`。檢查只在隔離的本機 Miniflare D1 執行，不讀寫正式資料。預設每個遷移最多讀 20,000 列、寫 2,000 列。

- 先以歷史遷移匯入的資料量測，再從相同起點加入 2,000 個無關主體，以及每個主體在所有既有屬性的分數，重新執行待發布遷移。保留真實 schema、索引、限制與 triggers；建立測試資料的成本不計入遷移。
- 兩組資料都要符合讀寫預算。使用預設預算的遷移，若無關資料讓讀取或寫入增加超過 `max(100 列, 原量測的 10%)`，也直接阻擋。這可抓出整表掃描，以及先掃描某屬性全部分數、再篩選指定主體的非唯一索引查詢。
- 必須遍歷資料的批次作業可用獨立一行 `-- d1-row-budget: reads=<整數> writes=<整數> reason=<原因>` 宣告預算。宣告只豁免成長差額檢查，兩組實測仍須低於宣告值。
- 待執行檔案不存在、D1 未回傳有效計數，或測試資料建立失敗時，檢查失敗，不以零成本通過。若歷史起點尚無屬性資料表，只做原始資料量測。

回歸測試保留已發布的 0134 原文：原始資料讀取 1,536 列，擴充後為 7,536 列，寫入同為 666 列；新版守門會阻擋。只修正其中一處 JOIN 仍須失敗，兩處都由指定的 30 個主體驅動索引查找才可通過。歷史遷移不改寫。

這些是樣本與成長檢查，不能稱為正式資料庫的精確成本或上限。目前擴充情境涵蓋屬性主體與分數，沒有模擬帳號、規則、投票歷史的成長；涉及其他資料量的遷移需補相應情境。

### 屬性重播驗證

- 使用 `node --import tsx scripts/benchmark-attribute-replay.ts` 在隔離的本機 Miniflare D1 比對 1 萬、5 萬、10 萬筆合成投票。投票集中於單一屬性且配對各不相同。程式逐次列出 D1 回傳的讀寫列數和本機耗時，再比對兩條路徑的即時計分表、配對計數與公開快取分數。可在指令末尾加票數以單獨驗證。
- 正式排程以 `attribute_replay_scheduled` 記錄結果、耗時和 D1 計數，量測範圍從進入屬性重播到釋放鎖，包含每日查詢是否有待續跑的工作。目錄 outbox、遊戲快取和清理工作在量測範圍外。失敗時記錄已收到 D1 結果的 SQL 統計。追蹤同一輪工作時，合計各次 `pending` 與最後一次 `replay`，並另行檢查失敗紀錄。
- 單一屬性的歷史超過 8 塊或 1 MB 時，逐塊排序後最多四路合併，記憶體同時只保留各路當前區塊及當批結果。直接評分和比較票分兩趟按原順序計算，每塊結果與游標原子保存。排序計分期間固定輸入範圍。追加的純比較票可在完成後接續處理，較早的比較票仍可能使受影響屬性重算。
- 新增高頻讀取端點時，必須補測試說明快取命中、過期備援及 D1 查詢範圍。
- 屬性總表與遊戲列表各自擁有版本游標與 IndexedDB 快取；投票頁的「我的收藏」直接重用屬性總表快取，在本機完成 BGG ID 交集與題目抽選。屬性總表以自己的 snapshot、delta entries 與 `throughVersion` 同步，遊戲列表的變更不需要讓屬性總表重新讀完整資料。
- 舊的 `GET /api/attributes/vote-subjects` 已停用並不再查詢 D1；不能讓舊書籤或舊前端重新觸發未受限的主體目錄掃描。
- 舊的 `GET /api/attributes/question` 已移除；抽題完全由已載入的本機目錄完成，答案寫入時由伺服器驗證目前有效的屬性與遊戲。
- 公開遊戲頁禁止 `COUNT` 或 JOIN 投票明細；規則列上的聚合票數由唯一投票列的 INSERT/DELETE trigger 原子維護，且投票不得改動規則內容版本時間。
