# 屬性投票收票與批次計分

## 收票成功的意義

`POST /api/attributes/responses` 先驗證並保存一筆原始回答或完整排序。
投票 ID 唯一，重送不覆寫原始票。排序仍保留參考遊戲的位置；目前計分政策仍只比較玩家遊戲的中心向外相鄰順序。

收票交易與計分交易分開。計分忙碌、租約失效或交易失敗，都不撤銷已保存的票，也不要求手機重新送票。
回應的 `scoreStatus` 區分 `applied` 與 `pending`；兩者都表示雲端已收票。真正的收票寫入失敗仍回傳錯誤。
`updatedValues` 在忙碌時可以是空陣列，活動資訊則來自已保存的原始票。

## 唯一計分者與共用進度

- 日常計分、完整重算及分段重算共用 `attribute-replay` 租約，並與遊戲合併的既有鎖互斥。
- 上傳後嘗試取得租約。未取得者直接確認收票，不讀取計分批次或分數狀態。
- 取得者等待 20 ms，讓同時送達的票進入同批；以 `rowid > through_rowid ORDER BY rowid LIMIT 10` 取得新票。
- 同批按保存順序沿用既有計分公式，在記憶體合併同一遊戲的多次更新；每個受影響狀態只寫一次。
- 分數、共用進度、必要的歷史重算修訂，以及「確認已無新票才釋放租約」在同一個 D1 batch 交易提交。
- 提交前於交易內檢查租約 token、資料庫時間、原進度與歷史修訂。過期處理者不能覆寫新狀態。
- 空佇列檢查與租約釋放不可拆開：檢查前到達的票由原擁有者接續處理，釋放後到達的票可取得新租約。

單次最多處理兩批，控制 SQL 數量與計算量。達到預算的剩餘票留在 D1，由下一次上傳或既有每日維護繼續處理。
每日維護只增加一次有索引的待處理檢查，不新增週期排程；沒有工作時不寫入資料。
處理者突然中斷時，租約最多保留兩分鐘；後續處理先清理已到期租約，再從已提交進度繼續。
這不是即時處理的時限保證，持續超過處理能力的流量會累積待計算票。

## 舊資料、人工修改與重算

Migration 0127 只新增 nullable `online_weight` 與一筆進度，透過索引讀取既有歷史末端，不掃描或重寫全部舊票。
`online_weight` 由伺服器當下的登入權限決定；原有舊票或匯入票沒有此欄位，不會被日常計分重複採用。
完整歷史重算仍依現有角色權重與規則計算。

新的線上收票會明確指定大於歷史末端及已處理進度的 rowid，避免刪除末端後 SQLite 自動重用已處理的 rowid。
進度同時保留對應投票 ID；錨點消失或被重新編號時停止增量處理，等待完整重算建立新基準。

完整重算及分段重算發布最終結果時，會核對歷史末端，並在同一交易更新線上進度。
重算期間仍可收票；若新票使完整重算的末端驗證失敗，重算交易回復，已收票不受影響。
人工改寫、刪除原始票或變更角色的修訂檢查也會阻擋正在提交的過期增量計算。

## 本機驗證與成本範圍

執行 `node --import tsx scripts/benchmark-attribute-ingestion.ts`。
使用隔離的真實 Miniflare D1、正式 migration、正式收票與計分程式，包含索引、trigger 與目錄發布。
程式也注入進度提交失敗，確認原始票保存、分數及進度回復、之後由伺服器補算。

2026-11-19 的同樣十張六款排序票量測：

| 處理方式 | 讀取列數 | 寫入列數 | 讀取分數的處理者 | 單請求最大 SQL 數 |
| --- | ---: | ---: | ---: | ---: |
| 新程式逐張上傳、各自計分及發布 | 3,112 | 692 | 10 | 26 |
| 新程式十張同時上傳、合併處理 | 790 | 107 | 1 | 26 |
| 加入十萬筆歷史後，十張同時上傳 | 790 | 107 | 1 | 26 |

這是本機 fixture 的量測，不代表正式站的容量、延遲或 CPU 時間上限。
列數包括收票驗證與目錄發布，不含網站 session middleware；也不是與舊版正式程式的直接比較。
短時間內涉及不同遊戲的票較難合併狀態寫入，實際節省會依投票內容與抵達時間改變。
免費 D1 的每日讀寫額度與其他功能共用，必須持續以正式站 metrics 觀察。

`scripts/attribute-online-scoring.test.ts` 覆蓋忙碌收票、提交回復、交接時新票、分批續算、重算與刪除末端。
`tests/core/attribute-concurrent-votes.spec.ts` 使用十個獨立手機瀏覽器，以原生 tap 同時送出六款排序，驗證真實 API、計票數與冪等重送。

## 與既有正式版直接比較

本機最後成功發布紀錄為 `244f1b830a4142ce34adb6403b6f301aa75066e9`。
執行 `node scripts/compare-attribute-ingestion.mjs 244f1b830a4142ce34adb6403b6f301aa75066e9`，
由 Git 載入該版本的程式及 migration，與工作樹新版分別建立獨立 D1。兩者使用相同遊戲、初始分數、索引及十張投票。
舊版遭遇衝突的重送成本也計入，以兩邊最後都保存、計算十張票作比較。驗證查詢不計入投票成本。

| 十張票的情境 | 舊版讀取 | 新版讀取 | 舊版寫入 | 新版寫入 |
| --- | ---: | ---: | ---: | ---: |
| 兩兩比較，每隔兩秒 | 1,234 | 1,354 | 304 | 284 |
| 擴充組合兩兩比較，逐票處理 | 1,594 | 1,694 | 304 | 284 |
| 六款排序，每隔兩秒 | 5,452 | 3,112 | 832 | 692 |
| 擴充組合六款排序，逐票處理 | 6,469 | 4,069 | 835 | 695 |
| 相同六款排序，同時上傳 | 5,686 | 790 | 832 | 107 |
| 十組不同六款，同時上傳 | 19,698 | 2,670 | 2,560 | 755 |
| 十萬筆歷史，相同六款同時上傳 | 5,686 | 790 | 832 | 107 |

常態兩兩比較每票多讀約 12 列，增幅 9.7%，並非所有情境都減少讀取；寫入減少 6.6%。
六款排序即使沒有併發，讀取仍減少約 43%、寫入減少約 17%。
上述兩種同遊戲併發試驗中，舊版首次接受一張、其餘九張需重送；新版首次接受全部十張。
每份最終狀態都與該資料庫實際保存順序的逐票計算精確一致。

對照時修正了計分查詢先巡覽所有啟用屬性的計畫，固定從指定遊戲／屬性主鍵查詢；
小量收票驗證直接綁定遊戲 ID，較大的排序保留 JSON 路徑以遵守參數上限。
活動名稱等 metadata 與資格驗證分開；可投票資格在收票交易內核對一次，避免擴充組合的重複條件查詢。
分數 upsert 直接綁定資料、每頁最多 99 個參數；進度沿用已讀取的投票 ID，不再重讀末端資料。
租約、歷史修訂、進度及交易回復檢查均保留。

SQL statement 數與 D1 API 呼叫數分開計算。對照測試每次投票最多 17 次 D1 API 呼叫；
免費方案的每次 50 次限制對 `batch()` 視為一次呼叫，並非對每個 statement 計數。
見 [D1 官方限制](https://developers.cloudflare.com/d1/platform/limits/)。
以上是本機成本與正確性驗證；正式站的網路延遲、CPU 時間與持續高流量仍需部署後觀察。
