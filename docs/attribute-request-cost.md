# 完整屬性投票 API 的 D1 成本

2026-11-20。比較基準為 `321e75b`，本輪修改尚未部署。

## 重現與量測範圍

- `npm run check:attribute-cost`：以目前正式程式執行完整 HTTP 請求，檢查實際 D1 讀寫預算。
- `node scripts/check-attribute-request-cost.mjs --baseline=321e75b`：同一 fixture 比較修改前後，驗證分數、RD、直接評分及比較計數精確一致。
- `npm run check:attribute-cost -- --compare-ranking-model`：同一 fixture 比較現行相鄰計分與雙向原斜率整票。輸出在 `.wrangler/attribute-ranking-model-cost.json`。
- 可在命令最後指定 `ranking-member` 等情境。輸出在 `.wrangler/attribute-request-cost.json`，包含各階段與各 SQL 的列數。

使用獨立 Miniflare D1，所有 migration、Session 驗證、角色查詢、收票、trigger、計分、分數差額與最末 outbox flush 均使用實際程式。
只替換外部 rate limiter 的服務回應；Session 與角色沒有 mock，不呼叫 Google 或正式資料庫。
初始化、fixture 寫入與結果驗證不計入成本；不含畫面首次載入及其他 GET 請求。

## 雙向原斜率整票的線上計分成本

以同一套現行 migration、收票 API 與兩份獨立的 Miniflare D1 資料庫做對照。研究版只在測試 bundle 裡改用雙向原斜率模型，以一整張票更新相同的自選遊戲。保留現行活動與證據計數的格式，也共用查分、租約、批次寫回及分數差額發布。確認計分後分數或 RD 確實有改變，並比對 D1 meta 和 HTTP 讀寫標頭。

13 個情境每版各送 10 張票。兩版在本次量測的讀取列數、寫入列數、SQL 數量，以及各查詢分項的代價均相同。下表為每票平均 D1 計費列數。

| 情境 | 現行讀／寫 | 雙向原斜率整票讀／寫 |
| --- | ---: | ---: |
| 訪客六款，逐張送出 | 119.0／30.3 | 119.0／30.3 |
| 會員六款，逐張送出 | 121.0／30.3 | 121.0／30.3 |
| 編輯者六款，另顯示兩款參考遊戲 | 119.2／29.2 | 119.2／29.2 |
| 十人同時排同一組六款 | 56.0／7.8 | 56.0／7.8 |
| 十人同時排各自不同的六款 | 88.4／34.8 | 88.4／34.8 |
| 已有十萬張歷史票，十人同時排同一組六款 | 56.0／7.8 | 56.0／7.8 |
| 訪客一百款，逐張送出 | 1697.8／331.1 | 1697.8／331.1 |

訪客六款的分數狀態查詢一次取回六筆遊戲狀態，D1 平均計為 18.4 列讀取。狀態 upsert 平均為 22.8 讀／7.2 寫，發布分數差額及更新目錄版本合計平均 14.0 讀／13.0 寫。兩個排序方向共享已讀取的狀態，在記憶體合併後每款只寫回一次。D1 計費列數包含索引及其他查詢工作，因此高於邏輯上的六筆。併發數字取決於實際合批情形。本節量測範圍為收票到增量計分與發布，歷史重算和 Worker CPU 需另行量測。

## 每日共用寫入額度（後續加入）

訪客與一般會員的每次寫入會先檢查、再累加當日共用額度（`worker/data/writeBudget.ts`），編輯者與管理員不經過這一步。
以同一 fixture 量測，平均每票多約 2.8 列讀取、1.1 列寫入，例如訪客兩兩比較為 59.2／17.5、訪客六款排序為 119.0／30.3；
編輯者情境不變。發布成本檢查的各情境預算因此各放寬 3 列讀取、2 列寫入。

## 保留的修改

1. migration 0129 移除重複的版本索引。`catalog_version` 的 UNIQUE 索引仍保留，增量分頁與有界清理均可使用它。
   六款分數發布少維護六份索引項目，實測每票少六列寫入。
2. Session 仍每次查詢並檢查到期，再讀取最新角色；指定 Session 與會員主鍵查找，避免早期統計使查詢轉為掃描會員表。
3. 收票共用本次 Session 取得的暱稱與顯示設定。公開 JSON schema 不接受 `actorName`，前端無法偽造。
   無 Session 快照的內部呼叫保留單次查詢暱稱的相容路徑。
4. 同一屬性、最多 98 個計分目標時，屬性僅查一次，再查目標遊戲；混合屬性及大型目標集合保留一般 JSON 路徑。
   六款單次排序的計分階段實測少五列讀取，分數計算與處理順序不變。

收票交易內的即時有效性檢查、冪等 response ID、計分租約、歷史 revision 與進度交易均保留。

## 撤回的嘗試

將小型排序的 metadata 查詢從 `json_each` 改為 ID 的 `IN` 清單，六款時兩者均讀 20 列。
這個變體沒有省列，因此維持原本單一 JSON 查詢，沒有留下額外條件分支。

## 量測與回歸保護

- HTTP 讀寫標頭改在最外層資料庫 middleware 收尾時填入，涵蓋登入驗證與 route 返回之後的 outbox 工作。
- `DatabaseStatement.all()` 也計入 D1 回報的寫入，避免未來 `UPDATE ... RETURNING` 透過此入口時低估。
- 成功 HTTP 請求的兩個標頭逐筆與原始 D1 回傳 meta 的總和比對，並驗證有 metadata 工作時仍正確。
- 失敗查詢未提供的 D1 meta 無法由應用程式補出；這套數字不是 Cloudflare 帳務的替代品。
- 原本只檢查常數的假預算測試已移除。`test:release` 現在必須通過實際完整 API 成本檢查。
- 串行預算能抓出重複索引或主要查詢退化；併發預算保留批次時序的餘裕，不強迫測試恰好合成單一批次。
- 回歸涵蓋 Session 到期、下一次請求看到角色撤銷與隱藏暱稱、惡意 actor 欄位、重送冪等、98／100 款邊界、混合屬性與目錄版本分頁。

這是本機模擬 D1 與實際前後端程式的驗證，沒有執行正式站投票或第三方 Google 登入驗收。

驗證結果：完整測試 1,699 項通過、1 項既有略過；最後查詢調整後的重點測試 36 項通過。
型別、D1 邊界、trigger fanout 與檔案大小檢查通過。
實際本機前端／Worker／D1 的登入、手機投票、排序重試、併發與觸控瀏覽器測試 19 項通過。
完整 API 修改前後共 26 組情境，以及單獨執行的發布成本檢查 13 組均通過。
